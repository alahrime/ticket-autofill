# Ticket Autofill

Reads a photo of a handwritten notebook page and fills the open InvoMax invoice. Runs fully offline.

## Shop PC setup (Windows, once)
1. Install Python 3.11+ (tick "Add to PATH").
2. Install Ollama for Windows from ollama.com, then run: `ollama pull qwen2.5vl:7b` (~6 GB).
3. In this folder: `pip install -r requirements.txt`
4. Map InvoMax's fields (plan Task 5) in `invomax.py`.

## Use
Double-click `run.bat` (starts Ollama if it isn't running, then the app). Open or paste a photo, pick the job, check yellow fields and prices, click **Fill InvoMax**.

## Inspection report (Word)
Click **Inspection report**, then **Add photos** and pick photos of the printed state inspection receipts (the top half is enough; about a second each). Each receipt becomes one row: date, 2-digit year + make, last 6 of the VIN, mileage, 20.00. Yellow rows need a look (VIN check digit failed, year doesn't match the VIN, something missing): double-click a cell to fix it, Delete removes a row. Set the customer and page number, then **Save Word file**: rows are sorted by date and written into `report_template.docx`, 20 per file (`C&G P4.docx`, `C&G P5.docx`, ...), each with its PAGE label and TOTAL. The next page number is remembered in `report.json`.

## Inspection report on a phone
Open **https://inspect.japaneseautoservice1.com** on the phone: the landing page has two buttons, **Inspection report** (`/scan`, below) and **Shop tickets** (the shop link further down). For the inspection report, type the PIN once (Safari: Share → Add to Home Screen for an icon). Tap **Add receipt photos** as often as you like (select several at a time); they line up without being read. Then tap **Read all photos**: they are read one at a time on the shop PC (under a second each with Windows' built-in text recognition, tried at a few sizes; the slow vision model is never used from the phone). Yellow and red cards show the photo: tap it to see it full screen and fill in what's missing; Retry re-reads a red one; × removes a card. Photos are kept only until the page is closed. Then **Make Word file** and **Share / Email** (or the ⬇ link). Rows are kept in date order, only on the phone; nothing is stored on the PC and photos are only held in memory while being read. The shop PC must be on with `phone.bat` running (it starts Ollama and `phone.py`, which runs the Cloudflare tunnel with no window and restarts it within seconds if it stops; tunnel log in `cloudflared.log`; to start it at boot, put a shortcut to `phone.bat` in `shell:startup`). If the phone shows Cloudflare error 1033, `phone.bat` isn't running: double-click it.

One-time setup (done 2026-10-27): `cloudflared tunnel create inspection`; its config is `%USERPROFILE%\.cloudflared\inspection.yml` (tunnel id, credentials file, `inspect.japaneseautoservice1.com` → `http://localhost:8080`). The default `config.yml` there belongs to the older `station-api` tunnel and silently wins, so always pass `--config` with `inspection.yml`, also for `cloudflared tunnel route dns --overwrite-dns <inspection id> inspect.japaneseautoservice1.com`. The page asks for a PIN once per phone (kept for a year). The PIN is in `phone_pin.txt` (made at first start, git-ignored); edit it and run `start-shop.bat` to change it, which logs every phone out. After 5 wrong PINs in 10 minutes the page refuses all PINs for 10 minutes.

## Learning InvoMax (probe)
Double-click `probe.bat`: a small window opens. Click **▶ Start watching**, then use InvoMax as usual; **⏸ Pause** / **▶ Resume** at any time. It only watches: it never clicks, types or saves anything in InvoMax. It logs what changes (windows opening, box contents, where clicks land) to `probe/watch-YYYY-MM-DD.log`, and saves a picture of each InvoMax pop-up it can't read (choice boxes, Yes/No boxes, menus) to `probe/shots/`. The log holds customer data, so `probe/` is git-ignored and stays on this PC. Close the probe window to stop. `python probe.py map` dumps InvoMax's controls once.

## Trying a recipe on InvoMax (trial mode)
Double-click `trial.bat`. **This one is not read-only**: it runs one recipe per **▶ Run** click. Pick the recipe, fill its values (plate, search text, odometer…) and Run. **Dry run** is on by default and logs what it would do without sending anything; do a dry run first. Unticking it asks "Run <recipe> LIVE on InvoMax?" and it goes back on after every live run, so each live run is confirmed again. Run one stage at a time, and only after the owner's OK for that stage. Leave **Allow copy-back** off unless the owner agreed (it presses Ctrl+A, Ctrl+C in an InvoMax box).
- It only starts when InvoMax is maximized and shows what the recipe starts from (most need an empty invoice; `odometer` and `vehicle_open` use the customer on screen; `customers_exit` / `vehicles_cancel` need their window open).
- **Stop:** hold **Esc** or push the mouse into the **top-left corner** of the screen.
- It stops at the first surprise and never retries. Afterwards it says what is left: **clear the invoice by hand** (the tool never presses Clear) and close any window it names.
- Stage order: `customer_search`, `customers_exit`, `customer_by_plate`, `odometer`, `vehicle_open`, `vehicles_cancel` (the vehicle stages need the customer the plate lookup loads).
- Each step's check, what was seen and how long it took go to `probe/trial-YYYY-MM-DD.log`.

## Shop tickets (mechanic phones, admin)
Two links on **https://shop.japaneseautoservice1.com**, each with its own sign-in. (The customer check-in iPad is retired: `/checkin` now just opens the start page, and staff check customers in instead.)
- **`/admin` — owner. The admin types the whole invoice** (since 2026-11-16), so the mechanic can stay on the car. **New ticket** is one screen: first and last name, phone, plate, VIN, year / make / model, odometer, the mechanic (picked from the accounts), what the customer wants, notes, and every part and labor line with its price (part names from `parts.csv` pop up under a description and bring their code and prices). **Save ticket** keeps it on the board as Waiting; **Send to InvoMax** puts it on the shop PC's "Ready for InvoMax" list (it needs a mechanic and at least one line). The same button is on a job a mechanic checked in or is working on, and the admin can change any ticket until **Mark filled** (if you change prices after typing the invoice, change them in InvoMax too). Totals are before tax: InvoMax works out the tax and supplies once the invoice is in it. Review still works when a mechanic uses **Finish job**: fix anything, **Send back** (with a note) or **Send to InvoMax**.
- **`/tech` — mechanics (own phones).** Sign in with your name and your own 6–8 digit PIN. **My invoices** lists your tickets the admin has sent to InvoMax: open one to see it and to fix its lines, odometer, VIN or notes until it's filled (the admin and the shop PC see the change). The older way still works: **Accept** a waiting job, add each part (description, qty, price, and the labor to install it) or a labor-only line, the odometer and notes, then **Finish job** sends it to the admin for review. A mechanic sees waiting jobs nobody else was given, and their own; never deposits.
- **Mechanics can check customers in.** On `/tech`, **New customer** takes first and last name, phone and year / make / model (plate and what they need are optional), then **Check in**. It goes on the board as Waiting, given to nobody, for whoever accepts it. No prices, lines or deposits there: the admin adds those.
- **More on `/admin`.** Board (Waiting / Working / Review / Approved). The invoice is printed from InvoMax as usual (company copy signed by the customer, plus the customer's copy). Totals are before tax (InvoMax adds the tax and supplies). **Deposits** on any ticket until it's filled: amount, cash / card / check / other, date and a note; each is saved at once, can be removed, and goes on the InvoMax draft as a note (take them off InvoMax's total). Mechanics never see deposits. **Mechanics & admins** adds a mechanic (name + PIN) or another admin (password of 10+ characters), resets a PIN or password (that also signs them out and unlocks their name) and turns accounts off or on.

**Deleting tickets.** The admin can delete any ticket (**Delete** on the ticket), and a mechanic can delete a job they can see (**Delete job**). A pop-up names the ticket and its total first, and says if it has deposits. A deleted ticket leaves every list, phones included, but isn't gone: the admin's **Deleted** button (on the board) lists them, and **Restore** puts one back where it was.
- A deleted ticket that was Waiting, Working or Review **and has no deposits** is removed for good 14 days after it was deleted (the Deleted list shows the date). That's how old test tickets and jobs that never happened clear themselves.
- **Never removed:** a ticket with any deposit (the customer may come back after 14 days when parts are late; it shows "Kept (deposit)"), and an approved or filled one (it may already be in InvoMax, and a filled ticket is part of the customer's history). These stay in the Deleted list until you restore them.
- The newest ticket waits until there's a newer one, so a ticket number is never handed out twice.

Running it: double-click **`start-shop.bat`**: it starts the shop server (127.0.0.1:8081), the phone page with the Cloudflare tunnel for both `inspect.` and `shop.`, and Ollama. It stops any copy already running first, so it is also the way to **restart** (after an update, a password reset or a sign-in lockout); it never touches the Ticket Autofill window or InvoMax. Put a shortcut to `start-shop.bat` in `shell:startup` to start it all at boot. The tunnel config is `%USERPROFILE%\.cloudflared\inspection.yml` (ingress `shop.japaneseautoservice1.com` → `http://localhost:8081`, added 2026-10-29).
- **The shop server is now `shop-web`** (TypeScript, in the `shop-web` folder; it needs Node.js 26, installed 2026-11-18). It answers the same links, uses the same `tickets.db`, accounts and sign-ins, so nobody signs in again. It runs in a minimised window called **Shop server**: leave it open (closing it stops the shop links until the next `start-shop.bat`). If the server ever stops, that window starts it again after 5 seconds and writes a line in `shop.log`.
- **After an update** (a `git pull`) build it once, then run `start-shop.bat`: `cd shop-web`, `npm ci`, `npx nx build api`. That makes `shop-web\apps\api\dist\main.js`, the file `start-shop.bat` runs. Before the first switch, `node tools/switch-check.mjs` (in `shop-web`) runs every test and a trial server on a spare port and prints `ready` (it never touches the running shop or the real `tickets.db`). If the server isn't built, `start-shop.bat` starts the old Python server instead and says so in `shop.log`.
- **Daily copy:** `start-shop.bat` copies `tickets.db` to `tickets-backup-YYYY-MM-DD.db` the first time it runs each day (git-ignored; delete old ones by hand when you like). It's a safety net until the nightly backups come.
- **Going back to the Python server** (if something is wrong with the new one): run **`start-shop.bat python`** (in a Command Prompt in this folder, or a shortcut with `python` added after the file name). It stops the new server and starts `shop.py` as before; plain `start-shop.bat` switches back. On `shop.py`: deleted tickets stay hidden and can't be changed; there is no Deleted list and no Restore; nothing is removed after 14 days; mechanics can't check customers in; and Delete answers "Not available on this server." Everything else works as before. (`shop.bat` and `phone.bat` still start the old Python shop server and the phone page on their own, but only when that one isn't already running: a second copy can't open the same port.)

First admin: on the first start with no admin, the server writes a one-time code to `setup_code.txt` (valid 24 h, deleted once used). Open `https://shop.japaneseautoservice1.com/setup`, type the code and choose your username and password. Or, at the PC, in this folder: `node shop-web\apps\api\dist\main.js admin <username>` (also resets a forgotten admin password; on the Python server it's `python shop.py admin <username>`).

Sign-in limits: 5 wrong tries for a name lock it for 10 minutes, 20 in a day lock it for 24 hours, and 20 wrong tries from one connection lock that connection for 10 minutes. An admin's PIN reset unlocks a mechanic; a locked admin name is cleared by running `start-shop.bat`.

Data: tickets and accounts are in `tickets.db` on this PC (customer names and phones, hashed PINs and passwords; git-ignored), and so are the daily copies. Tickets are only removed by the 14-day rule above, and only unfinished ones with no deposit; nothing else is ever deleted from `tickets.db`. `shop_pin.txt`, `shop_secret.txt` and `mechanics.txt` from the earlier single-PIN version are no longer used and can be deleted.

On the shop PC: `run.bat` → **Shop tickets** lists the approved tickets (refreshed every 4 seconds) and shows the InvoMax entry sheet for the one you pick: customer and vehicle in InvoMax order, the lines, notes and totals, each with a Copy button (or **Copy everything**). Type it into InvoMax, then **Mark filled**. **Load into Ticket Autofill** (or double-click the ticket) puts it in the main window's fields, lines and notes. It reads the same `tickets.db` as the shop server and never touches InvoMax itself. After a shop server update, close and reopen it too.

Year / make / model suggestions come from `vehicles.json` (from NHTSA, committed; the server stays offline). Once a year, for the new model year, run `python vehicles.py` (needs the internet; re-run it if it lists failed requests) and run `start-shop.bat`. An approved ticket becomes an InvoMax draft with `tickets.to_draft(ticket, catalog)`; the InvoMax fill itself is still being built (see `docs/superpowers/HANDOFF.md`).
