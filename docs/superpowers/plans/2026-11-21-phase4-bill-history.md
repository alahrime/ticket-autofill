# Phase 4: Bill History, Backups and Suggested Prices Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Import every InvoMax bill and line into our own `invomax.db`, link filled tickets to their bills, show Bill history in a first React page, back up both databases nightly, and suggest part and labor prices on the admin's invoice entry from the shop's own history.

**Architecture:** A pure TypeScript Btrieve reader (`libs/invomax`) decodes copies of InvoMax's live tables; the API (`apps/api`) copies, decodes and upserts them into a separate SQLite file, `invomax.db`, on a nightly timer, a button and a standalone command. Bill history reads `tickets.db` with `invomax.db` attached. Job mapping rules live in `tickets.db` and are applied in memory over the imported lines. Suggested prices come from those mapped lines. A new Vite + React 19 app (`apps/admin-app`) serves the Bill history and Job mapping pages. `web/admin.html` gets the suggestions, the backup line and the buttons.

**Tech Stack:** Node 26.13.1, TypeScript (strict), Nx 24, Express 5, `node:sqlite` (including its `backup()`), Jest 30, OpenAPI 3.1 + Orval + TanStack Query, React 19 + Vite + Vitest + Testing Library, Playwright + `@axe-core/playwright`.

**Spec:** `docs/superpowers/specs/2026-11-21-phase4-bill-history-design.md` (owner approved 2026-11-21). Where it is silent, `docs/superpowers/specs/2026-11-18-typescript-shop-server-design.md` → "Customer history (phase 4)" still applies to backups and the Bill history API.

**Execution (owner's rule):** per task, one implementer subagent, then **two reviewer subagents**: (a) spec/correctness and (b) security/robustness. Fix until both approve, then commit. Push only when the owner says so. A review of the whole branch runs at the end. Work happens in a worktree on branch `phase4-bill-history`.

**Stages:**
- **4a** (Tasks 1–9): import, linking, backups, Bill history. The four-week limit applies to this stage.
- **4b** (Tasks 10–13): job mapping and suggested prices.

Tasks 1–4 are the critical path: they give the owner `node main.js import-invomax` while InvoMax is still paid for, even if the switch slips.

- **Never write, lock or rename anything in InvoMax's folder** (`C:\hunni\files` by default). Open its files only with `fs.openSync(path, 'r')`; libuv opens them with read/write/delete sharing. Never use `fs.copyFile`, because `CopyFileW` can refuse while InvoMax has the file open.
- **No customer data in git:**
  - Tests, fixtures and snapshots use made-up values only: JANE DOE / Jane Testcase, `(555)010-0000`, `XKS-4827`, `tst-0001`, and invoice numbers `9000001` and up.
  - Btrieve test files are generated by `libs/invomax/src/testing.ts`, never cut from real files.
  - Logs carry counts, invoice numbers and error class names, never names, phones or plates.
  - `probe/` stays git-ignored.
- **Git-ignored and never committed:** `invomax.db*`, `invomax-import/`, `backups/`, `shop-settings.json`, `shop-web/apps/admin-app/dist/`.
- **Rules for `tickets.db`:**
  - It is shared with Python. New data goes only in **new tables** (`invoice_finals`, `invoice_unlinked`, `job_map`), created with `CREATE TABLE IF NOT EXISTS` by the TS server.
  - Python's `tickets.py` must keep working and must not wipe them. Each new-table task adds a Python interop test.
  - No new ticket JSON fields.
- **`invomax.db`** is TS-only and opened in WAL mode. It can be rebuilt from InvoMax while InvoMax runs.
- **Money:** integer cents inside (`Math.round(real48 * 100)` for InvoMax values). The API sends dollars as JSON numbers (`45.5`), as the ticket API does.
- **Dates:** InvoMax `MMDDYYYY` becomes ISO `YYYY-MM-DD`. Times are local ISO with seconds and no offset (`nowIso()` from `@shop/domain`).
- **New endpoints:**
  - Admin only: `signedIn('admin')`, then `validRequest`, then the handler.
  - Each one is described in `apps/api/openapi.yaml`, with the client regenerated by `npx nx run api-client:generate` and committed.
  - Errors are `{error}` and never echo internals.
- **Config:**
  - A new optional `shop-settings.json` in the repo root: `{"invomaxDir": "C:\\hunni\\files", "backupTargets": ["D:\\shop-backups"]}`. A missing file means those defaults with no targets.
  - Env `INVOMAX_DIR` overrides `invomaxDir` (tests point it at a temp folder).
- **Times of day:** the nightly run happens at 02:00 local time; the backup goes first, then the copy to targets, then the import, then auto-linking.
- **Retention:**
  - `backups/tickets-YYYY-MM-DD.db`: the newest 90.
  - `backups/invomax-YYYY-MM-DD.db`: the newest 14, plus the first copy of each month for 24 months.
- **Import retries:** 3 retries, 1 minute apart, after a failed decode or a count mismatch. Only one import runs at a time, across the server and the command, using the lock file `invomax-import/.lock` (created with `'wx'`; a lock older than 30 minutes counts as stale).
- **Linking window:** InvoMax date from the ticket's filled date −1 day to +3 days. The plate is normalised to upper case with only A–Z and 0–9.
- **Suggestions:**
  - Levels: make + model with year ±2, then make + model, then make, then all.
  - Each level needs at least **3 samples in the last 24 months**; if no level has that, the same levels run over all time.
  - The price is the median; the range is the 25th–75th percentile. Prices are per unit and taken before discount.
  - The labor price is multiplied by `qty`. If there's no history, `parts.csv`'s price is used.
- **Dependencies:** pin exact versions in `package.json` (no `^`). Add only what a task names.
- **Python tests stay green:** `for f in tests/test_*.py; do python "$f"; done` prints `ok` for each. `node tools/parity-guard.mjs` passes, since `shop.py`, `tickets.py`, `accounts.py` and `pinweb.py` don't change.
- **Commits:** commit only your own files. Messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push.

## Review Focus

1. **InvoMax writes a bill while we copy.** A torn copy fails to decode, or its count doesn't match the header. The import retries and never stores a partial set; `invomax.db` keeps the last good import. Test in Task 4.
2. **A bill edited or deleted in InvoMax after we imported it.** The newest version wins and the change is counted. A bill missing from a later file is kept, with `gone_at` set; it is never deleted. Test in Task 4.
3. **The admin's link decisions win.**
   - A link the admin made, undid or marked "none" is never redone automatically.
   - One InvoMax bill never links to two tickets.
   - Test in Task 6.
4. **A suggestion arrives after the admin typed a price.** The typed price stays: the lookup is asynchronous, and the admin may type while it runs. Test in Task 13.
5. **Rolled back to `shop.py`.** `admin.html` then gets 404 from the new endpoints (status line, buttons, suggestions). It must behave as it does today, with no error flash and no broken line. Tests in Tasks 8 and 13.

    - `im_invoices`: `ImInvoice` columns, plus `first_seen`, `updated_at` and `gone_at` (`''` while present). Indexes on `date`, `plate`, `phone` and `name`.
    - `im_lines`: `ImLine` columns (plus the line's `date`), plus `year`, `make`, `model` and `trim` from `parseVehicle`. The primary key is `(invoice_no, line_no)`, with an index on `code`.

  - `importOnce(config: Config, opts?: { sleep?: (ms: number) => Promise<void>; now?: () => Date; vehicles?: Vehicles }): Promise<ImportResult>`. It works like this:
    - It takes the lock, or else returns `{ok: false, error: 'already running'}` without recording a row.
    - It copies `INVOICE.btv` and `DETAIL.btv` into `importDir` with `copyTable` and decodes them.
    - On a `BtrieveError` it retries up to 3 times, sleeping 60 000 ms between tries.
    - It upserts everything in one transaction. A changed `hash` replaces that invoice's lines and counts toward `changed`. Invoices missing from this file get `gone_at = now`; an invoice that comes back gets `gone_at = ''`.
    - It records an `im_imports` row and logs `invomax import ok <invoices>/<lines> +<added> ~<changed> -<gone>` or `invomax import failed <ErrorClass>` in `shop.log`, then releases the lock.
  - `copyTable(src: string, dest: string): void` copies with `openSync(src, 'r')` and a read/write loop to `dest + '.tmp'`, then renames.
  - `lastImport(db: DatabaseSync): { finished: string; ok: boolean; invoices: number } | null` returns the newest row and `lastGoodImport(db): string | null` returns the newest `finished` with `ok = 1`.

### Task 5: Backups, restore and copy to USB

**Files:**
- Create: `apps/api/src/backup.ts`, `apps/api/test/backup.spec.ts`
- Modify: `apps/api/src/cli.ts`, `main.ts`, `shop-web/README.md`

**Interfaces:**
- Consumes: `Config` (Task 4) and `openImDb`.
- Produces:
  - `backupNow(config: Config, now: Date): Promise<{ tickets: string; invomax: string | null }>`.
    - It writes `backups/tickets-YYYY-MM-DD.db` and, if `invomax.db` exists, `backups/invomax-YYYY-MM-DD.db`.
    - Each is written with `node:sqlite`'s `backup(source, dest + '.tmp')` from its own fresh read connection, checked with `PRAGMA quick_check` = `ok`, then renamed.
    - It overwrites that day's file. A failure throws, and the `.tmp` is removed.
  - `pruneBackups(dir: string, now: Date): string[]` deletes per the retention rule and returns the removed names. It never touches other files.
  - `lastGoodBackup(dir: string): Date | null` reads the newest `tickets-*.db` date in the name. `backupHealth(dir: string, now: Date): { last: string | null; stale: boolean; offsite: string | null }`, where `stale` means no good copy in 2 days and `offsite` comes from `backups/offsite.json` `{at, target}`.
  - `copyBackups(dir: string, target: string, now: Date): { copied: number; skipped: number }`.
    - It copies to `<target>`, creating it, and skips a file of the same size and name.

  - `suggest(samples: Sample[], car: { year: number | null; make: string; model: string }, now: Date): Pick | null`, where `Pick = { unit: number; count: number; low: number; high: number; basis: Basis }`.
    - `type Basis = { level: 'model_years' | 'model' | 'make' | 'all'; years: [number, number] | null; make: string; model: string; recent: boolean }`.
    - The levels run in order, each first over the last 24 months (`recent: true`) and needing 3 or more samples; then the same levels over all time. It returns null if there are no samples at all.
    - `model_years` is skipped when `year` is null.
    - The median of an even count is the mean of the middle two. `low` and `high` are the 25th and 75th percentiles by linear interpolation (numpy's default). All are rounded to whole cents, half up.
  - `GET /api/price-suggestions?code&year&make&model&qty` (admin, in OpenAPI; `qty` defaults to 1 and must be 0 < qty ≤ `MAX_QTY`; `code` is required) returns `{ part: Suggestion | null, labor: Suggestion | null }`.
    - `Suggestion = { price: number; count: number; low: number; high: number; basis: Basis | { level: 'catalog' } }`, in dollars.
    - `labor.price`, `low` and `high` are already multiplied by `qty`; `part` is per unit.
    - If there's no history, the `parts.csv` price is used with `count: 0` and `basis.level: 'catalog'`, or null if the code isn't in `parts.csv` or its price there is 0.
